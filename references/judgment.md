# 判断规则：从信号到单元数

`core/signals.py` 输出事实，这份文件把事实变成"这个目录有几个最小单元"。

**每条规则都能写成一句话：「看到 X，所以 Y」。X 必须可复核。**

---

## 第零步：名实一致性检查（在一切判据之前）

**所有结构判据都隐含假设"名字能反映内容"。如果名字本身是错的，判据就失去意义。**

所以在应用任何判据之前，先做这一步：

```
1. 列出实际的 3–5 个文件名（不是目录名）
2. 提取它们的统一前缀 / 共同特征
3. 和目录名比对
```

| 结果 | 处理 |
|---|---|
| 一致 | 继续用判据 |
| 不一致 | **目录名不可信，一切判断以文件名为准** |

### 三种不一致

**A. 名实不符**（名字方向对，粒度错）
```
目录名 Compressed，内容确实都是压缩包
但混着 ROM / 游戏 / 工具 → 粒度不对，按内容重新判
```

**B. 名字指向另一件事**（名字整个是错的）
```
目录名是「某部作品名」，内容是「某画师作品 01~37」
→ 完全无关，是资源站打包时套错的壳
```

**C. 名字是空壳**（内外同名嵌套，但内容不一致）
```
A\A\
→ 必须比哈希，不能假设外层是壳
```

### 实测教训

一个目录叫 `20200702 妹と一緒に楽なことをする♡`（某百合游戏名），
实际内容全是同一前缀的 `某画师作品 (n).mp4/jpg`（写真集）。

**整个名字属于另一部作品。** 五轮判断都拿这个名字当证据，前四轮全错。
直到打开看文件名才知道。

```
不要用目录名断定内容性质
不要用目录名推断主题
目录名只用来形成假设，证据必须是文件名和结构
```

## 嵌套同名目录：必须比一次

看到 `A\A\` 这种结构，**先比哈希再决定**：

```
相同 → 字节重复，只报告；未经批准不删除或覆盖任何一份
不同 → 两个独立单元（可能是不同版本、不同批次）
```

| 情况 | 判断 |
|---|---|
| 内外完全同哈希 | 外层或内层是重复拷贝 → 1 个单元 |
| 内层有内容、外层只有 1 个子目录 | 外层是传输壳 → 1 个单元，可拍平 |
| 内层只有空子目录 | **不能断定外层是壳** —— 先看外层自己有没有文件 |
| 内外同名但哈希不同 | 两个独立单元，各自成立 |

**"内层是空壳"这个判断必须实际 `ls` 过内层，不能从体积推算。**

## 一、绑定型信号 → 1 个单元，整块

### has-unity-layout

```
信号: unity-layout = true
       （同层存在 *.exe 和同名的 *_Data/ 目录）

结论: 1 个单元，整个目录是不可分割的整体

依据: Unity 引擎的固定布局——可执行体通过同名的 _Data 目录加载资源，
      拆开任何一个都无法启动。

注意: 即使 composition 看起来"混乱"（bin + arc 混在同一层），
      也不能按类型拆。引擎要求同级存在。

反例: 只有 exe 没有 _Data → 可能只是安装包，按普通软件处理。
```

### has-vm-disk

```
信号: vm-layout = true，且 vm-disk-count > 0

结论: 1 个单元，整个目录

依据: 虚拟机的磁盘分片（.vmdk）配合 .vmx/.vmsd/.nvram 才构成一台可启动的机器。
      单独拿走任何一个分片，虚拟机即报废。

注意: 分片数可能是几十个。不要因为"文件多"就认为该拆。
```

### engine-payload

```
信号: engine-payload-count > 0

结论: 倾向 1 个单元，但需确认执行体在同层

依据: .pak/.bundle/.assets/.resS 是引擎的打包资源，脱离执行体没有意义。

反例: 整个目录只有资源包、没有 exe → 可能是某个游戏的资源备份，
      或者是资产商店下载的资源。这种情况也是 1 单元，但需标注"资源包"。
```

### save-binding

```
信号: save-binding = true（同层存在 save/ saves/ 存档目录）

结论: 存档与当前目录绑定，整个目录 1 个单元

依据: 存档默认写在游戏目录内。移动游戏本体但不移动存档，等于丢进度。

注意: 拍平套壳、改名、搬移时，必须连存档一起走。
```

### bin-plus-data

```
信号: bin-plus-data = true（有二进制 + ≥2 个数据/资源子目录）

结论: 倾向 1 个单元

依据: "程序 + 多个资源目录"是典型的安装体布局。

注意: 这条比 has-unity-layout 弱。仅凭它不足以定论，
      要看是否还有 manifest（package.json / .sln 等）。
```

## 二、序列型信号 → 该序列 1 个单元

### sequence-detected

```
信号: sequence-detected = true 且 coverage >= 0.7

结论: 该序列 = 1 个单元。序列以外的文件各自独立。

依据: 统一前缀 + 连续编号 = 同一部剧/同一门课的分集。
      缺集不否定这个判断——缺的是内容，不是边界。

注意: 
  - coverage < 0.7 时降级为 uncertain。可能是编号复用，不是同一序列。
  - "series" 的范围是 prefix 相同的那些文件。同名但编号不连续的，分开算。
  - 一个目录里可能有多个序列（不同 prefix），各自成单元。

反例: 34 集网课平铺在一个目录里，没有外层文件夹。
      按"散落文件"算是 34 个单元；按"同一门课"算是 1 个。
      → 正确答案是 1 个。判据是"用途相同"，不是"有没有外层文件夹"。
```

### volume-parts

```
信号: volume-parts = true

结论: 该分卷组 = 1 个单元

依据: part01-08 / .001-.008 缺一不可，缺卷的解压不出来。

注意: missing 非空时，标注"分卷不完整"，但仍然算 1 个单元
      （不完整是内容状态，不是边界问题）。
```

## 三、到达型信号 → 弱证据，只作辅助

### name-content-match

```
信号: name-content-match = false
       （文件名的统一前缀，不在目录名里）

结论: 目录名不可信，一切判断以文件名为准

用法:
  1. 先看 content-prefix 是什么（这是内容的真实身份）
  2. 再看 prefix-ratio——占比越高越可信
  3. 用 content-prefix 重新形成假设，再验证

依据: 实测中目录名可能整个指向另一部作品——
      目录名是一个百合游戏，内容全是另一个画师的写真集。
      五轮判断都拿这个名字当证据，前四轮全错。
```

**这一条优先级最高——它在所有结构判据之前生效。**

### nested-same-name

```
信号: nested-same-name = true

结论: 必须比哈希才能判断是否重复

四种情况:
  内外完全同哈希          → 字节重复，报告关系，不删除或覆盖
  内层有内容、外层只有 1 个子目录 → 传输壳 → 1 个单元，可拍平
  内层只有空子目录        → 不能断定外层是壳，先看外层自己有没有文件
  内外同名但哈希不同      → 两个独立单元

依据: "内层是空壳"这个判断必须实际 ls 过内层，不能从体积推算。
      实测中曾错误断定"内层只有空子目录"，实际内层有完整重复的 40 个文件。
```

### reparse

```
信号: reparse-count > 0

结论: 这些是 Junction/符号链接，指向别处

规则:
  - 绝对不跟进去（会重复计数）
  - 绝对不移动、不改名（会断开链接）
  - 计 0 单元，单独列在报告里

依据: 实测中 23 个 Junction 全部指向同一目录树的其他位置。
      跟进去会让 330 个游戏变成 660 个。

额外: Junction 的 target 是绝对路径。移动父目录会让所有链接失效。
      如果必须移动，先记录所有 target，移动后重建。
```

### batch-arrival

```
信号: batch-arrival = true（≥30% 的子项在同一秒创建）

结论: 不能单独定论。只说明"这些是一起出现的"。

依据: 同秒创建 = 一次复制/解压/下载。这证明的是"怎么来的"，
      不是"是不是一件事"。

用法: 
  - 作为其他信号的佐证（如 unity-layout + batch-arrival → 更确定）
  - 作为"需要进一步验证"的提示
  - 不能作为"这是一组"的唯一理由

反例: 三个不同主题的目录在同一秒创建（同一次下载的产物），
      但主题互不相关 → 3 个单元，不是 1 个。
```

### time-span

```
信号: span-days

用法: 
  - span 很短（<7 天）+ 类型一致 → 倾向一批导入，可能是一组
  - span 很长（>1 年）+ 类型混杂 → 长期积累，几乎肯定是多个单元

注意: 这条只调置信度，不做结论。照片集可能跨 3 年但仍是"我的照片"一个组。
```

## 四、独立性信号 → 倾向多个单元

### composition

```
信号: file-count / dir-count / kind-count

规则:
  kind-count >= 4 且 无绑定信号 且 无序列信号
    → 倾向容器，内部多个单元

  kind-count <= 2 且 file-count >= 5
    → 倾向单一单元（同质集合）

注意: "类型多"不等于"该拆"。一个游戏目录里有 exe/dll/pak/jpg/ogg，
      kind-count 可能 5+，但它是 1 个单元（unity-layout 优先）。
```

### is-shell

```
信号: is-shell = true（目录内只有 1 个同名子目录，0 文件）

结论: 外层是传输壳，内层才是本体 → 整体 1 个单元

依据: 解压时多套了一层。内外创建时间通常同秒。

动作: 可以拍平（把内层提为外层），但不是必须的。
      拍平时要连内部所有内容一起搬，包括存档。
```

### reparse-count

```
信号: reparse-count > 0

结论: 这些是 Junction/符号链接，指向别处

规则:
  - 绝对不跟进去（会重复计数）
  - 绝对不移动、不改名（会断开链接）
  - 计 0 单元，单独列在报告里

依据: 实测中 23 个 Junction 全部指向同一目录树的其他位置。
      跟进去会让 330 个游戏变成 660 个。
```

## 五、信号冲突时怎么做

优先级从高到低：

```
1. 绑定型（unity-layout / vm-layout）
   一旦命中，其他信号全部忽略。这是硬约束。

2. 序列型（sequence / volume-parts）
   命中则是 1 个单元，但只覆盖该序列的范围。

3. 独立性（composition）
   只在无绑定、无序列时生效。

4. 到达型（batch-arrival / time-span）
   只调置信度，不做结论。
```

**绑定型最强的原因**：它是功能性的——拆开就坏。其他都是启发式的。

## 六、信号都没有命中时

三步法：

```
第一步  读文件头（不看扩展名）
        抽 3 个不同样本，看魔数是否一致
        一致 → 同一类文件，可能是一组
        各异 → 混杂，倾向多个单元

第二步  比时间戳
        同秒 = 批量到达
        跨年 = 长期积累

第三步  看结构
        有没有 exe + 数据目录
        有没有配置文件
        有没有存档目录

三步都做完还判不出 → uncertain，报给人，不猜
```

**`uncertain` 是合法产出。** 宁可多一条待定，不要多一条错判。

## 七、新增判据的门槛

判据不能随便加。要加，必须满足：

```
1. 能写成「观察到 X，所以 Y」
   X 必须是可复核的事实（文件头、时间戳、目录结构），不是印象

2. 有硬证据支撑
   "看起来像垃圾" → 不能进
   "8MB 整 + 前 32 字节全 FF + 含 UEFI 特征串" → 能进

3. 说清反例
   什么情况下这条不成立

4. 能被代码化（理想情况）
   能在 signals.py 里实现 → 加
   只能靠语义理解 → 写进本文件的"三步法"
```

**判据的目的不是覆盖所有情况，是让"拿不准"这件事有明确的出口。**
